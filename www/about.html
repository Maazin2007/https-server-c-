// about this project

Built from
first principles

Most developers use frameworks that abstract away networking entirely. This project does the opposite — every layer is hand-written, from the TCP socket to the HTTP response headers. The goal was to understand what actually happens when a browser makes a request.

// how it was built

Build order

STEP 01

TCP socket

Started with socket(), bind(), listen(), accept(). Got a raw "Hello World" response working over curl before touching HTTP at all.

STEP 02

HTTP parsing

Read the raw request bytes, extracted the first line, split by spaces to get method and path. No regex, just string operations.

STEP 03

File serving

Mapped URL paths to the /www directory. Used ifstream to read files, built proper HTTP/1.1 responses with Content-Type headers.

STEP 04

Multithreading

Moved client handling into its own function. Spawn a detached std::thread per connection so the accept loop never blocks.

STEP 05

Graceful shutdown

Registered a SIGINT/SIGTERM handler. Sets atomic<bool> running to false, closes the server socket to unblock accept(), exits cleanly.

STEP 06

AWS deployment

Compiled on an EC2 Ubuntu instance, opened port 8080 in the security group. This page is being served by that machine right now.

// interview prep

Questions I can answer

Q: why a thread per client instead of async I/O?
Thread per client is simpler to reason about and sufficient for demonstrating concurrency. The next step would be a thread pool to bound resource usage, or epoll-based async I/O for production scale.
Q: where could a race condition occur?
The cout logging in handleClient — multiple threads writing to stdout simultaneously can interleave output. Fix: wrap cout calls in a std::mutex lock_guard.
Q: what does accept() actually do?
It blocks the thread until a client connects, then returns a new file descriptor for that specific connection. The original server fd stays open and keeps listening for the next client.
Q: why atomic<bool> for the running flag?
The main thread reads it in the while loop, the signal handler writes it. Two threads touching the same variable simultaneously without synchronization is a data race. atomic guarantees the read/write is indivisible.
